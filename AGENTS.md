# AGENTS.md

Этот файл — обязательная точка входа для любого нового агента в репозитории `n8n_ai_call_center`.

## Что читать в первую очередь

1. `docs/knowledge_base/09_PROJECT_CHANGELOG_AND_STATE.md`
2. `документация_для_агента/01_БЫСТРЫЙ_СТАРТ.md`
3. `документация_для_агента/02_ТЕКУЩЕЕ_LIVE_СОСТОЯНИЕ.md`
4. Если задача касается email-агента:
   - `docs/email_followup_agent/README_RU.md`
   - `docs/email_followup_agent/06_CHECKPOINT_RU.md`
   - `docs/email_followup_agent/05_TEST_REPORT_2026-04-29_RU.md`
5. Если задача касается live-звонков и ElevenLabs:
   - `документация_для_агента/04_ELEVENLABS_АГЕНТ.md`
6. Если задача касается серверного доступа, clean deploy, cron или live-путей:
   - `docs/knowledge_base/10_SERVER_ACCESS_147_45_213_87.md`

## Обязательный старт перед работой

Перед любыми правками нужно:

1. Выполнить:
   - `git -C /home/max/n8n_ai_call_center status --short`
   - `git -C /home/max/n8n_ai_call_center log --oneline -10`
2. Понять из checkpoint-документов:
   - что уже сделано;
   - на чем остановились;
   - что делать дальше.
3. Продолжать именно с этой контрольной точки, а не начинать новую ветку работы с нуля.

## Источник истины

Для этого проекта источником истины считаются:

- live-сервер `ai-core-prod-147` (`147.45.213.87`);
- live `n8n`;
- live `ElevenLabs`;
- актуальные checkpoint-документы в репозитории.

Локальный репозиторий — рабочая база кода и документации, но не надо автоматически считать его идеальным зеркалом live-сервера по всем runtime-файлам.

## Безопасный режим работы

- Не откатывать чужие изменения в грязном `git status`, если они не относятся к вашей задаче.
- Не считать untracked backup/runtime-каталоги мусором без проверки.
- Помнить, что в проекте есть реальные рабочие каталоги с пробелами в имени:
  - `Документация по скриптам `
  - ` Таблицы_контактов `
- Перед risky-правками на live сначала снимать backup и фиксировать точку отката.
- Не продвигать risky-правки сразу в `main`.
- Для боевых email-изменений учитывать, что email-контур отдельный и не должен ломать `AUTODIAL_DISPATCHER`.

## Обязательное обновление контрольной точки

После каждой значимой завершенной задачи обязательно обновлять:

- `docs/knowledge_base/09_PROJECT_CHANGELOG_AND_STATE.md`
- если затронут email-агент:
  - `docs/email_followup_agent/06_CHECKPOINT_RU.md`
- если изменилось live-состояние проекта:
  - `документация_для_агента/02_ТЕКУЩЕЕ_LIVE_СОСТОЯНИЕ.md`

## Обязательные поля checkpoint

В каждом checkpoint-документе должны быть явно и актуально заполнены разделы:

- `Сделано`
- `На чем остановились`
- `Что делать дальше`

Если задача изменила реальное поведение live-контура, эти три раздела нужно обновить в том же ходе работы, а не оставлять “на потом”.

## Отдельные правила для email-агента

Если работа связана с `email_followup_service.py`, таблицами `контакты_косметологов_москва_*`, SMTP, IMAP bounce, Telegram-отчетами или workflow `EMAIL_FOLLOWUP_AGENT_*`, обязательно:

1. Прочитать `docs/email_followup_agent/README_RU.md`.
2. Прочитать `docs/email_followup_agent/06_CHECKPOINT_RU.md`.
3. Проверить:
   - `systemctl status email_followup.service`
   - `/health`
   - текущее расписание live workflow
   - актуальный recipient Telegram-отчета
4. После изменений обновить:
   - `docs/email_followup_agent/05_TEST_REPORT_2026-04-29_RU.md`, если менялись реальные проверки;
   - `docs/email_followup_agent/06_CHECKPOINT_RU.md`.

## Чего нельзя делать

- Нельзя работать “как будто проект пустой”.
- Нельзя завершать значимую задачу без обновления checkpoint.
- Нельзя менять продовое поведение и не отражать это в документации.
- Нельзя молча оставлять расхождения между реальным live-состоянием и handoff-документами.
