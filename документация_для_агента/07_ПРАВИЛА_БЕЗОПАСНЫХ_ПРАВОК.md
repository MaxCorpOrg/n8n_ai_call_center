# Правила безопасных правок

## 1. Базовый принцип

Нельзя править несколько слоев сразу без необходимости.

Сначала понять, где проблема:
- телефония;
- ElevenLabs;
- n8n;
- память;
- Google Sheet.

Отдельно: нельзя тестировать risky-изменения сразу на live `Main`.

## 2. Если проблема в голосе и разговоре

Сначала смотреть:
- ElevenLabs prompt;
- LLM;
- TTS;
- turn-taking;
- interruption behavior.

## 3. Если проблема в контексте

Сначала смотреть:
- `context_fetch`;
- `postgres_memory`;
- SQL/таблицы памяти.

## 4. Если проблема в итогах звонка

Сначала смотреть:
- `call_log`;
- Google Sheet;
- формат `call_result` и `next_step`.

## 4.1. Если проблема в SMS

Сначала смотреть:
- `send_sms_info`;
- workflow `ELEVEN_TOOL_SEND_SMS_BRIDGE (draft)`;
- номер текущего звонка `system__called_number`;
- Mango SMS response `result`.

## 5. Что не трогать без необходимости

- `first_message`
- SIP-маршрут
- номер и trunk
- `voice_id`
- `tool_ids`, если сначала не снят live-config и не понятен состав tools
- live webhook URL tools
- правило `на этот номер` -> `system__called_number`
- server-level network/firewall
- live traffic routing на `Main`, пока новая конфигурация не проверена на staging

## 6. Как вносить правки

1. Считать текущее состояние.
2. Снять backup live-состояния до правки.
3. Если правка касается ElevenLabs prompt/tools/turn-taking, сначала делать её в test/staging-ветке, а не в `Main`.
4. Сделать минимальное изменение.
5. Прогнать 1-2 тестовых звонка на staging-ветке.
6. Только после этого переносить ту же конфигурацию в live `Main`.
7. Перепроверить live-конфиг после промоута.
8. Только потом делать следующую правку.

Текущая branch-дисциплина:
- GitHub:
  - `main` — stable/prod base;
  - `codex/eleven-agent-staging` — безопасная ветка под подготовку следующих изменений;
- ElevenLabs:
  - `Main` — stable live;
  - `staging-safe-test-2026-04-25` — test branch без live traffic по умолчанию.

Отдельно после правки в ElevenLabs всегда проверить:
- `LLM`
- `voice_id`
- `tool_ids`
- список active tools
- `disable_first_message_interruptions`
- что traffic всё ещё не ушёл случайно на test branch
- что `call_log` не получил жёсткую dynamic-variable schema на stable live

## 7. Чего нельзя делать

- “массовый рефакторинг”, если задача локальная;
- менять и n8n, и ElevenLabs, и память одновременно;
- публиковать новый сервис наружу без необходимости;
- предполагать, что docs важнее фактического live-состояния.
- возвращать старые backup-объекты tools в ElevenLabs без проверки актуальных `tool_ids`
- тестировать новую prompt/tool-схему прямо на live `Main`, если для этого не было отдельной staging-проверки
