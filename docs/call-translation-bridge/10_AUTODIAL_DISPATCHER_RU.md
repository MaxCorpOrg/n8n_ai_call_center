# 10. Автодозвон по таблице `Лиды_обзвон`

Этот документ описывает текущий live-контур автодозвона для LipoLong. Сейчас диспетчер работает в sheet-first режиме и использует Google Sheet как источник истины.

## Что делает контур

1. Берет контакты из Google Sheet:
   - `https://docs.google.com/spreadsheets/d/1FUHh8lS8pEx58eRK2Rt6AYn3cy6ogWSO32vZWqYw_Fc/edit?gid=199760593#gid=199760593`
2. Целевую вкладку выбирает по `gid = 199760593`, а не по жестко прошитому имени листа.
3. Читает историю и состояние прямо из той же таблицы:
   - исходные лиды;
   - lock-строки автодозвона;
   - строки `call_log` от ElevenLabs.
4. Ставит lock-строку через webhook `call_log` перед каждым outbound-звонком.
5. Запускает outbound-звонок только в окне `10:00–14:00` по МСК.
6. Останавливает кампанию, когда список реально исчерпан, и не запускает его заново автоматически.

## Что считать живым контактом

В дневной лимит входит только живой разговор, где человек снял трубку и начался диалог.

Технически dispatcher считает живой контакт так:
- строка `source_system = elevenlabs`
- есть `eleven_conv_id`
- `call_result` не входит в неуспешные статусы:
  - `busy`
  - `no_answer`
  - `timeout`
  - `outbound_request_failed`

То есть автоответчики, IVR, гудки, сбросы и неудачные технические попытки в дневной лимит не входят.

## Рабочие лимиты

- Рабочее окно: `10:00–14:00` МСК.
- Предпочтительный пик: `10:00–12:00` МСК.
- Максимум живых разговоров в день: `15`.
- Максимум автодозвонов на один номер в день: `2`.
- Если по номеру уже был живой или содержательный контакт в текущем месяце, новый cold-touch по автодозвону не стартует до следующего месяца.
- Исключение из месячного stop-rule: явный клиентский callback, уже согласованный в разговоре.
- Максимум общих статусов недоступности на номер: `3`.
- После третьей недоступности номер помечается как нерабочий и исключается из автодозвона.

## Как работает sheet-first runtime

### 1. Выбор кандидата

Dispatcher сначала резолвит нужную вкладку по `gid`, затем читает весь лист и выбирает следующий контакт по правилам:
- не `do_not_call`
- не `final`
- не превысил дневной лимит автодозвонов
- по номеру не исчерпан месячный лимит cold-touch без явного callback
- у него уже наступило `next_call_at` либо оно пустое
- в день ещё не исчерпан лимит `15` живых разговоров
- у строки есть валидный номер в формате `E.164`; пустые и кривые номера не уходят в outbound и не создают холостые `validation_failed` execution'ы
- все appended outcome-строки канонизируются обратно к исходной seed-строке из импорта:
  - если у истории по номеру в `lead_id/source_record_key` уже успел оказаться сам номер телефона, dispatcher всё равно резолвит его назад в стабильный `row_*`
  - в live это нужно для нормальной трассировки звонков, чтобы outbound и `call_log` не теряли связь с исходной строкой таблицы
  - после фикса canonical `sheet_row_number`, `lead_key` и `source_record_key` для номера берутся из seed-записи, а не из последних appended outcome-строк

### 2. Lock через `call_log`

Перед outbound-звонком dispatcher добавляет строку в `call_log` с:
- `source_system = autodial_dispatcher`
- `call_result = dialing`
- `next_step = autodial_dialing`
- `next_call_at = now + dial_timeout_minutes`
- `notes_short = Автодозвон: взят в работу`

Эта строка играет роль:
- блокировки на время вызова
- счетчика попыток
- журнала истории

### 3. Outbound-звонок

После успешного lock dispatcher вызывает существующий webhook:
- `POST /webhook/eleven/outbound-call`

### 4. Обработка результата

Если outbound request не принят, dispatcher пишет вторую строку через `call_log`:
- `call_result = outbound_request_failed`
- `next_step = retry_after_failed_outbound`
- `next_call_at = now + 15 minutes` или `следующий день 10:15`, если дневной лимит уже исчерпан

Если звонок состоялся, итог уже пишет live-agent через `call_log`, и диспетчер видит это как обычную историю в таблице.

## Логика повторов

- В рамках одного дня dispatcher не звонит на один и тот же номер больше `2` раз.
- Если номер уже трогали в этом месяце и клиент не просил перезвонить явно, dispatcher не возвращает его в cold-очередь до следующего месяца.
- Если outbound request не принят или номер не ответил:
  - первая неудача -> повтор через `15 минут`, если окно `10:00–14:00` ещё открыто
  - вторая неудача в тот же день -> перенос на следующий день `10:15` МСК
  - статусы `no_answer` и `timeout` накапливаются как `unreachable_total`
- Если `unreachable_total >= 3`, номер переводится в архивный финал с заметкой `номер не работает`
- Статус `temporarily unavailable` трактуется как `no_answer`: без речевого сценария, только повтор по retry-политике
- Статус `busy` и любые машинные реплики вида `абонент сейчас не может ответить` трактуются как машинная недоступность: без продажной речи, только callback-логика
- Если окно уже закрыто, следующий шаг всегда уходит на завтра
- Если подряд накопилось `3` свежих `outbound_request_failed` за короткое окно, dispatcher включает `provider_circuit_breaker` и не продолжает бессмысленно жечь попытки
- Если за день накопилось слишком много чисто технических исходов без живых разговоров, dispatcher завершает с причиной `tech_waste_limit_reached`

## Что важно не ломать

- Не возвращать кампанию в начало после `exhausted`
- Считать в дневной лимит только живые разговоры, а не все исходящие попытки
- Не запускать outbound вне окна `10:00–14:00` МСК
- Не звонить одному и тому же номеру больше `2` раз в день, если клиент сам явно не попросил callback
- Не возвращать номер в новый cold-touch в этом же месяце, если уже был живой/содержательный контакт и нет явного callback
- Держать автодозвон и `call_log` на одном и том же `spreadsheet_id`, иначе dispatcher будет читать не ту очередь
- Не трогать live `call_log` как отдельную систему: он остается append-only журналом
- Не давать outcome-строкам перезаписывать canonical identity лида номером телефона; при разборе истории источником истины остаётся seed-строка `xlsx_import`
- Если таблица реально исчерпана, dispatcher должен завершаться с явной причиной `exhausted` и больше не брать новые номера
